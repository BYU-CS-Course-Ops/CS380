Run the Loop: Lab Tracker

Name

Every lasting project runs the same loop for every change: say what you'll change, make it on a branch, explain it, get a second reader, answer them, merge under the project's rules. Today you run it once, for real, on your own repository. Check off each step and write down the numbers as you go; they're what you'll hand in. The full steps and every command are on the Canvas page Git Workflow Lab Guide; this sheet keeps your place.

  • Every comment on mine answered: fixed (new commit, same branch), explained, or moved to a new issue

# after the merge git switch main git pull git log --oneline -5 git branch -D docs/link-design-doc

Part 3 · A merge conflict, on purpose12 min

  • A and B both branched from the same main, before either merged.  I'm:  A · B · both (solo)
  • A changed the README status line to "Design complete…"; B added an issue link to the same line
  • A's PR merged; B's now shows a conflict
  • B resolved it locally by merge, keeping both changes; pushed
  • B's PR reviewed and merged.  Conflict PR #

Our Git Standards

Project

Every project has rules for how a change gets in. On most, they're never written down, so every newcomer guesses and every maintainer applies them a little differently. Writing them down is the difference between a norm and a hope. Each decision below has a suggested default and some reasonable alternatives. Every one is your project's call. Choosing differently is fine; what isn't fine is a choice without a reason. Fill in your choice and one line of why, then copy it into docs/git-standards.md. That file becomes the heart of your CONTRIBUTING.md.

ReviewWho must read it before it merges? One approval from someone who didn't write itOr: two approvals; an owner for certain files. Solo: your review partner, or a self-review checklist when no one's available, said honestly Choice

Merge strategyWhat should main's history look like? Squash and merge: one commit per change; the steps stay in the PROr: merge commits (every branch commit kept); rebase and merge (every commit kept, and every one must be clean) Choice
Why
"Done"When is a change finished? Reviewed, merged, runs on main, docs updated if behavior changedOr: add "tests pass" once there are tests; "issue closed with a note" Choice

Optional: make GitHub enforce it. Settings → General → Pull Requests: allow only your merge method; if you squash, default the message to Pull request title and description; auto-delete head branches. A required approval is a branch ruleset (Settings → Rules). Solo: GitHub won't let you approve your own PR, so a required approval means every merge waits on your partner.
The test before you merge it: does the pull request that adds these standards follow them? Branch name, commit message, description, reviewer, merge method. A standard its own PR breaks isn't a standard.
