A release is a promise that everything in it is true. Teams at work run a release checklist before they ship; open-source projects check a release candidate before they tag it. The work isn't new writing; it's making each piece meet its bar. Mark each row twice: today, before you start (it tells you where to spend class), and tagged, just before you release.

Today's two work blocks: one item each

Block 1, before the test: fix what your tester is about to hit. The first of these that applies:

  1. The test is missing, isn't run by the setup guide's command, or fails.
  2. A file the tester reads is missing or false: setup, onboarding, README, starter issues.
  3. One of your two worst audit stalls is still there.
  4. Otherwise: the item furthest from its bar.

Block 2, after the test: one fix, the worst that fits. The earliest fail on your signed checklist, or else the earliest stall. Too big to fix? Log it properly instead: that's the block.

My block-2 item:

Before you tag, in this order

  1. Fix or log every remaining stall and fail. Logging is a known-issues line and an issue (good first issue if a newcomer could fix it). No new features.
  2. Bring every draft or missing row up to its bar.
  3. Finish the retrospective, checked against the signed checklist, and merge it.
  4. Run the test command from the setup guide on main. It passes.
  5. Tag and push: git tag -a v0.1-launch -m "launch" then git push origin v0.1-launch
  6. Submit the last row above.
Fix it or log it. Nothing ships undocumented, and nothing documented is untrue. CS 301R
